# ChCore OS 观察台

基于本仓库 Lab1 的本地 Web 实验工具。系统调用和定时器中断从 QEMU/GDB 读取真实执行现场；页表根据 Lab1 启动代码计算映射；调度、同步、互斥、程序/进程和 I/O 案例提供可交互的教学模型。实测与模型分别标注。

## 启动

在仓库的 `OS-Labs` 目录执行：

```bash
make -C Lab1 build
python3 Visualizer/server.py --port 8765
```

浏览器打开 <http://localhost:8765>。服务运行期间保留终端，结束时按 `Ctrl+C`。

环境需要 Python 3.8 或以上、`pexpect`、`qemu-system-aarch64`，以及支持 AArch64 的 `gdb-multiarch` 或 `gdb`。当前环境使用支持 AArch64 的 `gdb`。Lab1 还需要原有的交叉编译工具链与已完成的启动代码。

### 系统调用：用户态进入内核态

打开系统调用案例即可回放保存的观测记录。执行新的采集时，后端会启动 Lab1 的 QEMU 实例，通过 GDB 停在异常处理相关位置，在 ChCore Shell 中运行 `hello_world.bin`，读取现场并返回事件。按钮完成后，网页使用这次采集结果回放。

流程中的各个观察点：

1. 用户程序在 EL0 执行 `svc #0`，请求内核处理系统调用。
2. CPU 进入 EL1 的异常向量，保存返回地址和进入异常前的状态。
3. `sys_putstr` 处理输出请求。GDB 能读取本次传入的字符串。
4. 内核执行 `eret`，使用保存的状态和返回地址恢复用户程序。
5. 用户程序从 `svc` 后一条指令继续运行。

`CPSR & 0xf` 可以判断当前执行模式：`0x0` 为 EL0t，`0x5` 为 EL1h。EL1h 表示在 EL1 使用 `SP_EL1`。这个例子没有经过 EL2 或 EL3。

| 寄存器 | 含义 |
| --- | --- |
| `PC` | 当前指令地址；入口和返回前后可以看到地址变化 |
| `CPSR` | 当前处理器状态；低 4 位表示执行模式 |
| `ELR_EL1` | 异常返回地址，通常指向触发系统调用的 `svc` 后一条指令 |
| `SPSR_EL1` | 异常进入前保存的处理器状态 |
| `ESR_EL1` | 异常原因；`(ESR_EL1 >> 26) & 0x3f` 为异常类别 |
| `x8` | ChCore 系统调用号；这个输出案例的值为 `0` |

记录中的 `ESR_EL1 = 0x56000000` 对应异常类别 `0x15`，即 AArch64 的 SVC 异常。这里读取寄存器的工具是 GDB；用户程序不能直接执行 `mrs CurrentEL` 来读取当前异常级别。

保存的 [recorded-trace.json](data/recorded-trace.json) 来自 2026-10-14 的 QEMU/GDB 自动采集。五个事件属于同一次完整的 `sys_putstr` 调用：用户态的 `svc`、异常入口、内核处理、`eret` 和用户态恢复。该调用输出的是 `argv[0]: /hello_world.bin`，终端日志还记录了程序的其他输出。采集结果包含内核镜像 SHA-256 和原始串口、GDB 日志文件名，便于核对来源。

事件代表 GDB 停止的观察点。记录中的 `elapsedMs` 是主机完成整个采集的时间，包含启动、断点与调试控制开销，不能作为系统调用耗时。

新采集使用新的 QEMU 进程与 GDB 会话。用户程序地址可能变化，网页以这次采集的值为准。如果 QEMU 启动、程序运行或 GDB 读取失败，接口返回错误；不会把教学事件当作成功采集的数据。

采集接口也可以从终端调用：

```bash
curl -X POST http://localhost:8765/api/capture
```

采集时请等待当前操作完成，再开始下一次采集。服务端负责管理它启动的模拟器与调试器；独立终端中的 `make qemu` 是另一条运行路径。

### 启动页表：虚拟地址到物理地址

页面依据 [mmu.c](../Lab1/kernel/arch/aarch64/boot/raspi3/init/mmu.c) 中的 `init_kernel_pt()` 展示启动映射。内核高地址映射以 `KERNEL_VADDR = 0xffffff0000000000` 为基址，物理地址由虚拟地址减去该基址得到。

| 物理地址区间，右端不包含 | 属性 | 映射粒度 |
| --- | --- | --- |
| `0x00000000` 到 `0x3f000000` | Normal Memory | L2 的 2 MiB 块 |
| `0x3f000000` 到 `0x40000000` | Device Memory | L2 的 2 MiB 块 |
| `0x40000000` 到 `0x80000000` | Device Memory，局部外设 | L1 的 1 GiB 块，仅高地址启动映射 |

前两个区间同时存在低地址恒等映射和内核高地址映射。后一个区间对应高地址页表中额外的设备块。区间以外的地址应显示为未映射。

这个案例展示的是源码定义的启动页表规则，并不实时读取正在运行的进程页表。用户程序的随机地址、进程运行后的页表修改，以及缺页处理不在这一版本的采集范围内。

### 线程调度：时间片与就绪队列

调度页面用 Round Robin 模型演示线程在运行、就绪等状态之间的变化，以及时间片到期后队列如何轮转。它适合比较不同时间片产生的交替执行效果。

模型中的线程、时间单位和执行顺序由网页生成。它不是 ChCore 四核调度器的实际事件记录，也不据此推断内核中的切换次数、执行耗时或公平性。后续接入调度采集时，需要在内核的调度与上下文切换位置记录真实事件。

### 中断：异步事件与线程切换

模型中的定时器独立计时。IRQ 被屏蔽时保持 pending；多个定时信号可以合并。解除屏蔽的模型比较需要重新开始。中断发生于指令边界，与程序主动执行 `svc` 不同。

“采样中断”会启动独立 QEMU/GDB 会话，实际观察 `irq_el0_64`、`handle_timer_irq`、`__eret_to_thread` 中的 `eret`，以及返回后的 EL0。入口断点同时检查 BCM2836 每核 IRQ 来源寄存器的 `0x2` 位，确认物理非安全定时器。

入口之前的用户指令没有直接采样。`SPSR_EL1` 说明被打断的状态是 EL0，`ELR_EL1` 是保存的用户地址。中断可能触发调度，因此 `eret` 恢复的线程和地址可以不同。IRQ 的来源由设备寄存器与处理函数确认，不能把旧 `ESR_EL1` 当作本次 IRQ 的原因。GDB 调试耗时不代表真实中断延迟。

系统调用与中断记录分别保存，采集中断不会覆盖系统调用回放。中断接口为：

```bash
curl -X POST -H 'Content-Type: application/json' \
  -d '{"case":"interrupt"}' http://localhost:8765/api/capture
curl 'http://localhost:8765/api/trace/last?case=interrupt'
```

### 同步与互斥

同步模型用 empty/full 信号量预留空槽和数据，并用互斥锁保护队列。消费者先执行会等待 full，缓冲区满时生产者等待 empty；释放资源会唤醒等待者。预留资源后，信号量计数不一定等于可见槽位数量。

互斥模型把 `counter++` 分成 LOAD、ADD、STORE。默认交错会让两个线程读到相同旧值，复现丢失更新。互斥模式保护完整读改写过程，等待队列中只有获锁线程能继续。这里展示的是算法，不是 ChCore 线程的实测轨迹；内核提供 futex 与 notification 等待/唤醒原语。

### 程序与进程

程序文件是静态模板，进程是其运行实例。模型展示 ELF 段装载、cap_group、vmspace、PMO 和主线程，以及 READY/RUNNING/BLOCKED/EXITED 状态。相同数据 VA 在不同实例中映射到不同 PA，修改一个实例不会改变另一个实例。示意 PID 和地址不代表实际分配；ChCore 实际调度的是线程。

### 程序查询与 DMA

程序查询反复读取设备状态；中断 I/O 在设备准备期间允许 CPU 执行其他工作，但增加中断进入与确认。两种方式都由 CPU 搬运数据。

DMA 模型把搬运交给控制器，CPU 负责描述符、启动与完成确认。可以改变字数与每步搬运量，观察目标缓冲区和 CPU 工作占用。模型不包含总线竞争、地址映射或缓存一致性，不据此推断真实性能；它没有实现或启用 ChCore DMA 驱动。

## 验证

模型测试需要 Node.js；运行网页和真实内核采样不需要 Node.js。

```bash
python3 -m unittest discover -s Visualizer -p 'test_*.py'
node Visualizer/test_models.cjs
```

模型检查涵盖信号量资源守恒、互斥所有权、丢失更新、地址空间隔离、退出回收，以及 I/O 传输完成和 CPU 工作占用。浏览器验证包括 320、390、768 和 1440 像素宽度，以及实际 IRQ 采样。

## 范围与排查

本工具控制本地 Lab1 实验，不提供浏览器终端、任意程序执行或内核代码在线编辑。当前真实采集范围是 `hello_world.bin` 输出系统调用与物理定时器 IRQ。其他案例保留模型标识。

如果采集失败，先用 `make -C Lab1 qemu` 确认能进入 ChCore Shell 并运行 `hello_world.bin`。退出该模拟器可按 `Ctrl+A`，再按 `X`。构建失败时，应先处理 Lab1 的构建日志；服务日志中的 GDB 或 QEMU 错误用于定位采集问题。

仓库既有的评分脚本及 `change_serial` 工具问题与此 Web 工具分开处理。启动观察台不需要运行 `make grade`。
